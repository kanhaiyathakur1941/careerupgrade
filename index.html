Backend + System Design + AI Engineering + Career Execution

One evolving product for an experienced full-stack/backend developer. Build a multi-tenant document assistant in a single repo, reach a defendable production RAG system by Week 24, then add agents. 0. Rules — Follow These Strictly

Rule 1 — Don't restart

Your Laravel/PHP, SQL, Linux and AWS experience is the foundation. Python is the language new AI work will hire you in. Laravel stays on the resume as proof you have operated real products.

Rule 2 — One repo

Every week extends the same multi-tenant document assistant. Interviewers grill one system for 45 minutes. Seven shallow apps are weaker than one product with tenancy, failure, cost, and trade-offs.

Rule 3 — Learn by exit criteria

A topic is not complete until you can explain it, implement it, debug it and discuss its production trade-offs.

Rule 4 — Apply at Week 24

Start interviews when the RAG system is explainable. Agents, Kafka, and Kubernetes come after that gate. Do not treat Week 32 as the day you are allowed to apply.

Recommended study load: about 5 hours/day. Use roughly 2h learning + 2h building + 30m review + 30m interview/system-design practice. If a weekly deliverable is unfinished, cut new theory. If your production experience is under about 3 years, stretch Weeks 1–2 into four weeks. If it is 4+ years, keep the compressed Python start.

V4 — What Changed From V3

32 weeks, then apply

The job-ready core ends at Week 24. Weeks 25–32 add agents on the same product. Kafka and Kubernetes sit after you are already interviewing.

One product

A multi-tenant document assistant accumulates auth, workers, deploy, ingestion, RAG, evals, and agents. Same repository every week.

Evals from the first LLM week

Week 8 ships a streaming endpoint plus a 20-question eval file. The set grows to 100 questions with RAG. Quality is measured the week the feature exists.

Market gaps filled

Real document parsing, LangGraph after a raw tool loop, one MCP server, traces, and a small LoRA/PEFT comparison that stays a note, not a research track.

V4 principle: Learn fewer technologies deeply, connect them through one production-style product, and prove every major skill through explanation, implementation, debugging and trade-off discussion.

  • Resume rule: Laravel stays as proof; Python leads the new system.

Not added, on purpose

How to Learn — One Loop Every Week

Do not collect courses. Official docs plus a broken-and-fixed implementation beat another playlist.

1. Read narrow

Read the official doc for one topic only. The reference library on this page is the source list.

2. Build in the repo

Implement it inside the document assistant without following a full tutorial.

3. Break it

Cause a timeout, a bad PDF chunk, a duplicate job, or a prompt injection. Then fix it.

4. Write one page

Add a trade-off note to the README: what you chose, what you rejected, and what failed.

5. Say it aloud

Explain the week in five minutes with no notes. If you cannot, the week is not done.

Use the current job when it is safe. A production story from work — an incident, a slow query, a queue, a tenant bug — is stronger interview evidence than a side project that only you have run.

2. Backend Foundations

These are engineering fundamentals, not technologies to collect. They explain what your backend is actually doing underneath the frameworks. Fold them into the weeks below. Do not open a second curriculum.

Computer Science + Operating Systems Fundamentals

Learn

  • CPU, memory, storage and I/O basics.
  • Processes vs threads and context switching.
  • Blocking operations, file descriptors and sockets.
  • Virtual memory and memory-management concepts.
  • Signals, process lifecycle and graceful shutdown.
  • Concurrency vs parallelism.
  • Race conditions, locks and shared state.
  • Python garbage-collection and memory concepts.

Exit criteria

Given a slow or stuck API, explain whether the bottleneck is CPU, memory, disk, network, database or external I/O and show how you would investigate it.

API Design — Explicit Career Skill

Learn in order

  • HTTP methods, status codes, headers and content negotiation.
  • Resource modeling and REST conventions.
  • Request/response schemas and consistent error formats.
  • Pagination, filtering and sorting.
  • API versioning and backward compatibility.
  • Idempotency keys and safe retries.
  • Rate limiting and quotas.
  • Authentication vs authorization.
  • OpenAPI contracts and documentation.
  • Webhooks, callback security and signature verification.
  • API gateway/reverse proxy concepts.

Exit project

The document assistant's versioned API: idempotency, pagination, validation, standard errors, authentication and OpenAPI documentation.

Background Workers — Bridge to Distributed Systems

Learn

  • Why work should leave the request/response path.
  • Producer → queue → worker architecture.
  • Job states, retries and exponential backoff.
  • Dead-letter queues and poison messages.
  • Idempotent workers and duplicate delivery.
  • Scheduled and delayed jobs.
  • Redis-backed workers and SQS.
  • When a simple background task is enough vs a real queue.
  • Worker concurrency and graceful shutdown.

Exit project

The document-ingestion worker: retries, idempotency, failure handling and a dead-letter path.

Performance Engineering

Learn

  • Latency, throughput, concurrency and saturation.
  • p50, p95 and p99 latency.
  • CPU and memory profiling concepts.
  • Database query profiling and EXPLAIN ANALYZE.
  • Connection pools and pool exhaustion.
  • Cache hit/miss behavior and cache stampede.
  • Load testing and benchmark design.
  • Async I/O vs CPU-bound work.
  • Finding bottlenecks before optimizing.
  • Performance regression testing.

Exit project

Load-test the document API, identify its top bottleneck, optimize it, and document before/after latency and throughput. Heavier performance work waits until after you are interviewing.

ML / AI Fundamentals — Small Foundation, Not an ML Career

Learn

  • Supervised vs unsupervised learning.
  • Classification vs regression.
  • Training, validation and test data.
  • Features, labels and inference.
  • Overfitting and underfitting.
  • Loss functions and gradient descent conceptually.
  • Precision, recall, F1 and confusion matrix.
  • Neural-network and transformer concepts at a high level.
  • Training vs inference and inference cost/latency.
  • Fine-tuning vs prompting vs RAG, including what LoRA/PEFT changes and what it does not.

Scope rule

Understand enough to make engineering decisions and communicate with ML specialists. Week 30 is one small PEFT run so you can compare it with RAG. Do not spend months becoming a model-training researcher.

Python — Professional Backend Level

Must learn

  • Core syntax: variables, types, operators, conditionals, loops, range, continue, break, match.
  • Data structures: list, tuple, set, dict; mutability, copying, unpacking, comprehensions.
  • Functions: positional/keyword-only args, *args/**kwargs, scope, closures, annotations.
  • OOP: classes, composition, inheritance, protocols/duck typing, dunder methods.
  • Modules/packages/import system; project layout for the one repo.
  • Exceptions and custom exceptions; context managers.
  • Iterators/generators; decorators.
  • Type hints, generics, Protocol, TypedDict, dataclasses.
  • Virtual environments, pyproject.toml, dependency locking and packaging.
  • File/JSON handling, pathlib, datetime, logging, environment configuration.
  • Testing with pytest, fixtures, mocks and integration tests.
  • Asyncio, async/await, tasks, concurrency vs parallelism, blocking I/O.

Pace

Weeks 1–2 cover this for an experienced backend developer. Map each idea to something you already do in PHP: requests, validation, queues, tests. Skip tutorial clones.

Do not overdo yet

  • C-extension development, metaprogramming and advanced internals are optional until a real project needs them.

Reference: Python official tutorial.

FastAPI + Pydantic — Production API Engineering

Learn in order

  • Application structure, routers, path/query/body parameters and response models.
  • Pydantic validation, nested models, serialization, settings/config.
  • Dependency injection and reusable dependencies.
  • Middleware, lifecycle/startup/shutdown and exception handlers.
  • OpenAPI, Swagger/ReDoc and API documentation.
  • Authentication/authorization: JWT, OAuth2 concepts, API keys, RBAC, tenant checks.
  • Async database access and connection pooling.
  • SQLAlchemy models, sessions, transactions and migrations with Alembic.
  • Pagination, filtering, sorting, idempotency and API versioning.
  • Background tasks/queues, streaming responses.
  • Testing endpoints, integration tests and contract thinking.

Exit criteria

The document assistant API runs with PostgreSQL, auth, migrations, Redis, tests, logging and Docker. The LLM route streams and records token usage.

PostgreSQL + SQL — Database Engineering

Learn

  • Relational modeling, normalization/denormalization and constraints.
  • SELECT/JOIN/GROUP BY/HAVING/subqueries/CTEs/window functions.
  • Indexes: B-tree, composite, partial, expression; index selectivity.
  • EXPLAIN/EXPLAIN ANALYZE and query plans.
  • Transactions, ACID, isolation levels, locks and deadlocks.
  • MVCC concepts, connection pooling and long-running transactions.
  • Replication, read replicas, backups/restore and partitioning concepts.
  • Schema migrations and backward-compatible database changes.
  • Row-level tenant isolation for organizations and documents.
  • When PostgreSQL is enough vs when NoSQL/search systems are justified.

Exit project

Schema for the assistant: organizations, users, roles, documents, chunks, audit logs, usage events. Benchmark the hot queries.

Reference: PostgreSQL official documentation.

Redis — Caching + Fast State

Learn

  • Strings, hashes, lists, sets, sorted sets and streams.
  • TTL, eviction, cache-aside and write-through concepts.
  • Distributed locks, rate limiting, counters and idempotency keys.
  • Session storage, temporary state and job queues.
  • Cache stampede, stale data, invalidation and consistency trade-offs.
  • Persistence, replication, high availability and cluster awareness.

Exit project

Per-tenant rate limits and a cache in front of expensive reads. Measure before/after latency on the same API.

Reference: Redis documentation.

DSA — Front-load, Then Maintain

Learn

  • Big-O time/space complexity.
  • Arrays, strings, hash maps/sets.
  • Two pointers, sliding window, prefix sums, binary search.
  • Stacks, queues, linked lists.
  • Trees, BST, heaps/priority queues, tries.
  • Graphs: BFS, DFS, shortest path concepts, topological sort.
  • Recursion/backtracking.
  • Greedy and basic dynamic programming.

Schedule

  • Weeks 1–16: about 4 pattern problems per week. Patterns, not a random grind.
  • Weeks 17–24: 2 problems per week. Spend the saved time on system design and the RAG eval set.
  • Week 25 onward: 1–2 maintenance problems per week. Mock system-design and AI-design interviews take the rest of that slot.

Product companies still test DSA. AI startups weigh a production RAG/agent design more heavily. This schedule serves both without letting LeetCode eat the portfolio.

System Design — Core Career Pillar

Fundamentals

  • Requirements: functional/non-functional, constraints, assumptions.
  • Capacity estimation: QPS, storage, bandwidth, latency.
  • Availability vs consistency; CAP and practical trade-offs.
  • Vertical/horizontal scaling and stateless services.
  • Load balancers, reverse proxies and CDNs.
  • Caching, cache invalidation and distributed caching.
  • Databases: indexes, replication, partitioning, sharding.
  • Queues, pub/sub, event-driven systems and backpressure.
  • Retries, timeouts, circuit breakers, idempotency and deduplication.
  • Distributed locks, leader election and failure handling concepts.
  • Observability, SLOs/SLIs, alerting and incident response.
  • Security architecture and disaster recovery.
  • AI cost as a design constraint: tokens, context, model routing, queueing slow work.

Practice on paper, implement on the product

During Weeks 9–16 write two designs per week: URL shortener, notification system, file storage, feed, search, and the document assistant itself. From Week 17, one design per week is the AI system you are actually building: ingestion, retrieval, eval gates, and failure.

Document Parsing — The Hard Part of RAG

Learn

  • Plain text vs PDF vs office documents vs HTML.
  • Extracting text, headings, tables and page numbers.
  • OCR awareness for scans, and when OCR quality makes retrieval useless.
  • Cleaning headers, footers, hyphenation and boilerplate.
  • Metadata: tenant, source, title, updated time, access list.
  • Failed files, encrypted files, and huge files that must not block the API.
  • Idempotent re-ingestion when a document is replaced.

Exit project

Week 17: the worker accepts real PDFs, stores the original in S3, and writes cleaned text plus metadata to PostgreSQL. Include at least one deliberately bad file and show how the pipeline records the failure.

Embeddings + Vector Search + pgvector

Learn

  • What embeddings represent; semantic similarity.
  • Cosine similarity/distance concepts.
  • Vector storage and indexing in PostgreSQL.
  • Metadata filtering, including tenant and permission filters.
  • Top-k retrieval.
  • Chunk size and overlap trade-offs, measured on your eval set.
  • Hybrid lexical + semantic search.
  • Reranking.
  • Retrieval evaluation.

Preferred first implementation

Use PostgreSQL + pgvector. Add another vector database only when this product's scale or filtering needs force the move.

RAG — Retrieval-Augmented Generation

Pipeline

Ingest → parse → clean → chunk → metadata → embed → store → retrieve → rerank → construct context → generate → cite → evaluate.

Advanced topics inside Weeks 19–23

  • Hybrid retrieval.
  • Query rewriting and multi-query retrieval.
  • Metadata filtering.
  • Parent-child / hierarchical retrieval.
  • Reranking.
  • Document freshness and re-indexing.
  • Permission-aware retrieval for multiple tenants.

Leave for later

Graph RAG and multi-agent swarms are out of the first job jump. Mention them only if you can say why this product does not need them yet.

Exit project

Document Q&A that refuses unsupported answers, returns source references, and is scored by the eval set.

AI Evaluation — Starts Week 8, Matures Week 22

Learn

  • Create representative evaluation datasets.
  • Week 8: 20 questions for the streaming assistant. Behavior, format, and refusal cases.
  • Week 19 onward: grow the set as retrieval exists. Retrieval context precision/recall-style measurements.
  • Generation: relevance, groundedness/faithfulness and task correctness.
  • Week 22: 100 questions, slices by intent, regression checks in CI.
  • Human evaluation of a sample, not only automatic scores.
  • LLM-as-judge limitations and calibration.
  • Failure taxonomy and error analysis.
  • Offline evaluation before you widen access.
  • Online monitoring after deployment.

Exit project

A checked-in eval suite with expected behavior, measured retrieval and generation quality, and a note on which change helped and which change did not.

LLM Observability + Cost + Reliability

Track

  • Request ID, user/tenant, prompt/model version.
  • Input/output tokens, cost and latency.
  • Retrieval documents and scores.
  • Tool calls, errors and retries.
  • Model fallback frequency.
  • Cache hit rate.
  • Quality/evaluation score over time.

Reliability patterns

  • Timeouts, retries with backoff.
  • Fallback model/provider.
  • Circuit breaker.
  • Queueing for expensive workloads so the web process stays short.
  • Rate limits and tenant quotas.
  • Prompt or semantic caching when repeat questions dominate cost.

Tool

Use Langfuse or the same fields in your own structured logs. The interview answer is the trace, not the vendor logo.

AI Agents + LangGraph + MCP

Order is mandatory

  • Week 25: a raw loop you can read. Observe → decide → tool call → result → next action. Two or three tools, strict schemas, timeouts.
  • Week 26: the same workflow in LangGraph, with state you can draw.
  • Week 27: allowlists, human approval for sensitive actions, quotas, audit logs.
  • Week 28: one MCP server that exposes a real tool, such as tenant-scoped document search.
  • Week 29: traces for every tool call and model step.

Learn

  • Tool schemas and strict input validation.
  • Memory/state vs conversation history.
  • Single-agent workflows. Multi-agent swarms stay out of this roadmap.
  • Retries, timeouts and tool failure handling.
  • Human-in-the-loop.
  • Agent evaluation and trace analysis.
  • MCP: a small server your assistant actually calls, after you understand the tool boundary.

References: Model Context Protocol and LangGraph's docs when you reach Week 26.

Transformers / LoRA / PEFT — One Comparison, Not a Track

Scope

  • Tokenizer → model → generation pipeline.
  • Model cards, context limits and hardware constraints.
  • Quantization and inference-cost awareness.
  • Week 30: one small LoRA/PEFT run on a narrow task, then a written comparison with prompting and with RAG on the same questions.

What the note must answer

  • What data the adapter saw.
  • What improved, and what RAG still does better.
  • Training cost and inference cost versus an API call.
  • Why this product still uses RAG as the default.

Reference: Hugging Face Transformers docs and the PEFT docs for the single experiment.

8. After You Are Interviewing — Optional Depth

Start this only when applications are already going out, or when a specific job description requires it.

Kafka

An event pipeline on the same product if the role is a large distributed backend. Compare it with the SQS worker you already shipped.

Kubernetes

Deploy the API locally, then reason about probes, rollouts and limits. ECS/Fargate remains a valid production answer.

Heavier performance

A second load test after RAG and agents exist. Document p95, queue lag, pool exhaustion and cost per successful answer.
